# How t3boat works

Internals. For what t3boat is and how to install it, see the [README](../../../README.md).

```
T3 Code ──ws──> localhost proxy (t3boat) ──https/wss──> T3 server on a Boat sandbox
                    │                                     └─ watchdog: stops the sandbox when idle
                    └─ boat CLI: new / resume / host / exec / delete
```

- **Machine**: a Boat sandbox running the T3 server pinned to your desktop app's version, as a systemd user service bound to loopback. Boat relays a public HTTPS URL to it; T3's own pairing auth protects it.
- **Proxy** (`src-tauri/src/proxy`): one `http://localhost:<port>` per machine; that is the address T3 Code pairs with, so a new sandbox IP after resume never matters. The proxy is its own auth server towards T3 Code and uses its own long-lived token upstream.
  - Awake: frames pass through (minus `directEndpoints`, which would let T3 Code bypass the proxy). Snapshot-style subscriptions and some reads are recorded, and the images T3 Code loads are kept on this computer (`proxy/assets.rs`).
  - Asleep: answers pings, probes, config and other recorded subscriptions, and serves the shell and the chats from the state captured as the machine went to sleep, so opening a chat does not wake it. Images shown before stay visible.
  - Anything else wakes the machine: `boat resume`, then the held request goes upstream, then the socket closes so T3 Code reconnects to the live server and resyncs. A message sent to a chat is accepted at once instead, since a wake outlasts T3 Code's 15 s slow-request warning: it shows as sent, wakes the machine and goes upstream before T3 Code reconnects; one the server refuses is reported as a notification. Only the side information T3 Code asks for on its own as it starts and as a chat opens (git status, branch, terminals, servers, the pull request's badge and checks, linked chats, the count of older chats, the branch list, the changed-files count) never does: it is shown as last seen, and with nothing recorded it stays unanswered until the machine wakes for something else. Worktree setup progress, a chat's preview tabs and their events are never shown from a recording (a stale one would hold Send, or close or reopen tabs). What T3 Code asks for on its own but a person also waits for is shown as last seen too, but wakes the machine when never seen: the linked machines (Send), a pull request's details (a quick merge, the checks popover), a related chat's title, the automations and the archived chats (their settings pages), the chats under "Show more", the files of a commit or of uncommitted changes, an MCP app's tool definition and resources (a click in the app, an approved download), the voice status of the machine dictation goes to (a mic click). A project's settings page lists the project's images for its icon picker as it opens (`projects.searchEntries`, `imageOnly`, empty query): shown as last seen, else failed, and never a wake; typed into, the picker searches, and that wakes. Images never do either: one never seen on this computer shows as unavailable until the machine is next up. A finished command's output is kept the first time its row is expanded and shown from then on; one never expanded wakes the machine.
- **Streams** (`proxy/media.rs`): device and browser-preview streams pass through while the machine runs, close codes included. T3 Code opens them with a ticket the proxy issues itself and keeps retrying while one is on screen, so a stream never wakes a sleeping machine (it answers 503) and only input in it (a click, a key) counts as using the machine: watching does not keep it up. Any other WebSocket (dictation's `/ws/voice`, and whatever T3 adds) is relayed the same way but wakes the machine: a person opened it.
- **Linked** (`machine/link.rs`, `proxy/link.rs`): with linked environments on in T3 Code (Settings → Labs), every machine is linked into the desktop app's own T3 server through the proxy, with full access as the ceiling, so agents on this computer can work on it (`delegate_task`, the thread tools) with nothing to set up. Links last 30 days; each wake renews one in its last week. The link's status probe is answered from the last descriptor and never wakes the machine; a tool call does, and counts as using it. The handshake that opens a link's MCP session is given 3 s by T3, less than a wake can take, so for a sleeping machine the proxy answers it itself: the call that follows waits for the wake, the machine refuses the unknown session and T3 opens a real one.
- **T3 Connect** (`machine/connect.rs`): T3's own route for other devices (its phone app, a browser), a tunnel the machine dials out to Cloudflare under a stable hostname. "Turn on" runs T3's `t3 up --connect --headless --yes` on the machine, opens its sign-in page here and waits until the machine is reachable, then turns on "Hold webhooks while offline": T3 Connect's relay keeps a webhook sent to a sleeping machine (up to 24 h) and delivers it as the machine wakes. The tunnel comes back by itself on every wake. Nothing wakes a sleeping machine for a phone through T3 Connect: only t3boat on this computer wakes it.
- **Other devices over Tailscale** (`tailnet.rs`, MCP `add_to_phone`): so a phone gets what this computer gets (a sleeping machine that answers and wakes when used), it can pair with the proxy itself, as T3's own LAN pairing does: `http://<this computer's tailnet IPv4>:<port>/pair#token=…`, plain HTTP inside Tailscale's encryption. Each proxy has a second listener, bound to the address Tailscale reports for this computer (`tailscale status`, polled; never an interface scan, since 100.64.0.0/10 is shared address space) and following it as Tailscale connects and disconnects; the loopback listener does not depend on it. It is bound to Tailscale's tunnel interface too (`IP_BOUND_IF`, macOS only: elsewhere there is no tailnet listener), so a Mac that forwards packets does not take them for it from another network; the address and that interface are watched as a pair, and when another interface holds the same address, or Tailscale runs in userspace (no `TUN`), there is no listener. Its replies leave through the tunnel, so a peer that did not come through it cannot complete a connection. Requests with dot segments in their path are refused on both listeners, linking paths are matched as T3's router matches (any case, repeated slashes as one), and a media ticket opens only the streams, the preview tunnel and dictation, as T3's own. It answers only tailnet peers addressing it by that address, which DNS rebinding cannot produce, and refuses the linking paths (`/mcp`, `/oauth/mcp/*`) before any route; paths are checked with their dot segments resolved, as they go upstream. Phone tokens are kept apart from the desktop's (`device_tokens`), so pairing a phone does not count as T3 Code here having the machine; a code is redeemed only through the listener of the device it was made for, and MCP `remove_from_phones` revokes every phone's. Chats are captured in every encoding a client asked for in the last 3 days, so T3 Code here and on a phone of versions that encode differently keep each other's. A phone app asks for the server config with options of its own, so its first connection to a sleeping machine wakes it once; the recording then stays. Only while t3boat runs here. A device that has the machine already through T3 Connect adds the URL as a route of it, first. Provisioning names the machine in `/etc/machine-info`, so other devices show its t3boat name, not the sandbox's hostname.
- **CLIProxyAPI** (`machine/cliproxy.sh`, `machine/cliproxy.rs`), per machine and off by default: its Claude and Codex reach their models through CLIProxyAPI running on the machine itself, so they keep working with this computer off. `cliproxy.sh on` installs the pinned release (checksum-checked), runs it as the `t3boat-cliproxy` user service on 127.0.0.1:8317 with a key made on the machine, and points Claude Code (`~/.claude/settings.json` env `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`) and Codex (a `t3boat_cliproxy` provider in `~/.codex/config.toml`) at it; `off` takes exactly that back out and keeps the accounts. Provisioning applies the machine's setting on every upgrade and restore. Accounts are added with the proxy's own login on the machine (`-claude-login`/`-codex-login`; like a vendor sign-in, this app takes the browser's redirect on the same localhost port and replays it on the machine with `boat exec` (`machine/callback.rs`), so no tunnel process can outlive the app and keep the port), never copied from this computer: Claude's and Codex's refresh tokens are single-use, so two holders of one would invalidate each other at the next refresh. T3 counts Claude behind a custom endpoint as signed in whatever the proxy holds, and Codex's status as unknown, so the watchdog lists the proxy's accounts (vendor, email and routing priority, never a token) and t3boat decides from those who needs a sign-in. Individual accounts can be given priority `10` (or reset to `0`) by atomically updating `"priority"` in their credential file in `$HOME/.t3boat/cliproxy/auths/`, which CLIProxyAPI hot-reloads without restarting.
- **Antigravity** (`machine/antigravity.rs`): signed in with T3's own sign-in (`provider.auth.*`), never through CLIProxyAPI: T3 keeps the Google credential in a profile of its own per provider instance, which no CLI login reaches. As T3 Code's settings do, t3boat turns the default instance on (`server.updateSettings` upsert, enabled), installs Google's runtime there when T3 has none (`provider.install.start`, ~230 MB; never started for one that is there, since T3 would download the same release again), starts the sign-in and opens its Google link here. That page ends on an Antigravity page showing a code, not on a localhost redirect, so the code is pasted into t3boat (or given to an agent for MCP `answer_sign_in`) and goes to T3 with `provider.auth.respond`; a code T3 refuses leaves the field up for another try. T3 owns a sign-in by the session that started it, which is the proxy's token whatever the connection.
- **Watchdog** (`src-tauri/src/machine/watchdog.mjs`, on the sandbox): the machine decides when to sleep, so it finishes its work and then sleeps even with the laptop closed. Idle = no agent run in flight (incl. waiting on an approval), no sustained CPU use (a build), no "stay awake", no work due within 5 minutes, and nobody using it for 5 minutes: through t3boat, or in T3 from any other client (a phone through T3 Connect), seen as orchestration events only a person causes (opening a chat, pinning, archiving, ...). If T3 stops answering it counts as busy for at most 30 minutes; until it first answers after a boot it is starting, not failing. Before stopping it drains: publishes a manifest of orchestration high-water marks, the proxy captures that state and acks, the watchdog stops at that sequence (`boat stop self`) and says so. Before draining it saves the disk as a Boat snapshot (`boat snapshot self`, ~30 s); any use meanwhile calls the sleep off.
- **Scheduled work**: T3 runs automations, held webhook runs and an agent's resume after a usage limit on in-process timers, so on a sleeping machine they would not run, and T3 skips a daily automation it missed by over 10 minutes. The watchdog reports the next due time from T3's database; t3boat keeps it and wakes the machine 2 minutes ahead, for work that came due after the machine went to sleep (what came due while it ran had its chance). The watchdog then waits for it instead of sleeping. Only while t3boat runs: Boat cannot resume a sandbox on a timer.
- **Capture**: one shell snapshot, unfiltered, which serves every client whatever it asked to leave out; and the chats, one file each on this computer, named by thread id, thread sequence and snapshot encoding (`proxy/threads.rs`). A sleep fetches the files it is missing, most recent chat first, and deletes every other one: the files are the store, there is no index. It has 12 s for all of it, since the watchdog stops 20 s into a drain; a chat that did not make it wakes the machine when opened.
- **Capture freshness**: the proxy trusts its capture only when the watchdog confirmed stopping at the captured sequence and Boat's `stoppedAt` follows it. Otherwise (laptop closed while the machine ran) the first request that needs state wakes the machine once to resync. Recorded reads carry an epoch that moves on whenever an agent works or the user acts, so no outdated file or diff is served; recorded subscriptions (git status, terminals, ...) and the branch list a chat displays replay as last seen instead. The project's `t3.json`, which T3 Code reads on every chat open, follows the epoch too, so each sleep reads the recorded ones again: T3's editor saves over the file whatever it was shown, and a new thread's environment is decided from it. The automations T3 Code was shown are read again at each sleep as well: its editor saves every field of a task as it was shown. A branch search, a further page of branches and the one branch read T3 Code decides on (is this branch checked out in that worktree?) follow the epoch like any other read.
- **Expiry**: chats leave the store 3 days after they are settled, recordings 3 days after T3 Code last asked for them, images with the recording that points to them.
- **Resize**: Boat resumes a sandbox onto any size; an idle machine is moved right away and keeps its "keep awake", a working one (an agent or a build) moves when it next sleeps.
- **Upgrades**: on wake, a machine whose T3 version or provisioning scripts differ from the app's is re-provisioned (`provision.sh` is idempotent). A new T3 version also drops the recorded streams and stored chats: they are in the old server's encoding.
- **Keep-alive**: Boat keeps a stopped disk 14 days; machines asleep 12 days get a short wake.
- **Restore**: with t3boat not running for those 14 days the disk is gone. The snapshot saved at every sleep (`t3boat-<name>-<id>`, one of the plan's saved snapshots per machine) has no expiry: the next wake creates a new sandbox from it. The machine keeps its id, port and T3 environment; only its sandbox and addresses change.
- **Projects** (`projects.rs`, `machine/projects.rs`): t3boat moves no code itself; it drives T3 Code's own flow through T3's API. "Add a project" (in a machine's details, or picked when creating one) does what T3's "Add to another machine" dialog does: reads the project and its `.env` files from the desktop app's server (t3boat holds its own read-only session there, "t3boat" under Settings → Connections), then `projectClone.start` on the machine, which clones over HTTPS and registers the project with progress in T3 Code, then `projects.writeFile` for the env files. Private repos need nothing extra: Boat signs every sandbox in to GitHub as the Boat account (`gh` with git's credential helper, renewed on each resume), which T3's clones and pushes use. The machine's projects are read from its shell when it runs or sleeps, so listing them never wakes it. Work goes back the way T3 Code does it: push or open a PR. Agents use `add_project` here, or T3's own tools through the link (`t3_project_clone`, `delegate_task`, `t3_thread_launch` with the machine's `environmentId`).
